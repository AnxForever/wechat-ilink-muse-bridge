# 通道适配器契约（新增客户端时照这个写）

本仓库的 `ilink.py` 把**传输层**和**驱动层**分得很干净：传输层只负责
「把消息取出来」「把回复发出去」，驱动层（`ilink-watch.sh`）只负责
「可靠地排队、唤醒、回收、告警」。换一个聊天平台，换的只是传输层，
驱动层和 worker 契约可以原样复用。

`examples/muse-hook/`（微信）、`examples/qq-bot/`（QQ）和 `examples/feishu-bot/`
（飞书）是同一份契约的三个实现：三个 `*-watch.sh` 结构一一对应，worker 看到
的数据形状也一致（例如单聊统一叫 `c2c`，飞书在线上叫 `p2p`，由适配器在边界
翻译）。新增通道时按下面的清单核对，就不需要重新发明可靠性逻辑。

## 1. 必需的三个动词

一个通道客户端（Python，标准库即可）至少要提供：

| 动词 | 语义 | 硬要求 |
| --- | --- | --- |
| `poll` | 取一批新消息，打印 JSON | **绝不推进任何状态**（游标、去重表都不动） |
| `commit` | 提交一批，从 stdin 读 commit 块 | 幂等：同一块重复提交结果相同 |
| `send <to> <ctx> <text> --key <id>` | 发一条回复 | 同一 key 第二次调用必须回 `SEND_ALREADY_SENT` 且不重发 |

`poll` 的输出形状：

```json
{
  "msgs": [ { "from_user_id": "...", "message_id": "...", "kind": "text",
              "text": "...", "reply_to": "...", "chat_type": "c2c" } ],
  "filtered": { "dropped": 1, "senders": ["..."] },
  "commit": { "cursor": "...", "ids": ["..."], "files": ["..."] }
}
```

`msgs` 为空也必须返回 `commit`（空批次也要推进，否则游标永远不动）。
出错时打印一行 `POLL_ERROR:<原因>` 或 `NO_TOKEN` / `NO_CREDENTIALS` /
`NO_OWNER`，**不要打印空串**——驱动层把空输出判为崩溃并走告警。

可选但推荐：`typing <to> <start|stop>`（失败必须返回 0，它是装饰）、
`health`（exit 0/1/2）、`status`（JSON 快照）。

## 2. 六条不变量（不要重新发明）

1. **两段式提交。** `poll` 只取不提交；驱动层先把批次原子落盘，再调
   `commit`。崩在任何一步，下一轮重取——宁可重复，绝不丢失。
2. **原子认领 + 租约。** worker 用 `mv` 原子认领队列；处理期间每 ≤60 秒
   `touch` 一次处理文件。驱动层按 **ctime**（不是 mtime）超 10 分钟回收，
   且只在待处理队列为空时回收（否则 `mv` 会覆盖新批次）。
3. **幂等键持久化。** 发送前把 `(目标, 消息 id, 序号)` 落账本，成功才标
   sent；重试复用同一组值，靠服务端去重兜住「发成功但没收到响应」。
   拆气泡时 key 加后缀 `<msg_id>-1`、`-2`……序号必须是**确定性推导**的，
   不能随机（QQ 官方 SDK 的随机 `msg_seq` 就是反例）。
4. **发送前复查 + 合并连发。** 组织好回复、真正发出之前再查一次队列，
   有新消息就合并重写（最多 3 轮），一个突发只回一条。
5. **owner 白名单写在代码里。** 不在 `owner.json` 的发信人一律不进队列，
   但仍然要跟着 commit 块推进游标（否则队列会卡在一个永远不回复的人上）。
   陌生 id 记到 `unknown_senders.json` 供人工审批——绝不在聊天里审批。
6. **告警闭环。** 报坏也报好：首次异常立即报、之后每小时复报、恢复后
   报一次 `recovered`；抖动不满 10 分钟不报。

## 3. 拉模型 vs 推模型

- **拉模型**（微信 iLink）：驱动脚本每轮自己长轮询，`poll` 就是一次网络调用。
- **推模型**：平台主动推给我们，所以数据源是一个常驻进程（`<channel>bot.py
  serve`），先把事件**落盘**，`poll` 只是把已落盘的事件取出来。已经有两种：
  - **QQ 网关**：`qqbot.py` 落盘之后才持久化网关序号。
  - **飞书长连接**：`feishubot.py` 落盘之后才回 ack 帧（平台要求 3 秒内
    应答，否则按失败重推）。

推模型下有一条额外的硬要求：**先落盘、后确认**。确认的形态随协议而变——
QQ 是推进 `lastSeq`，飞书是回 ack 帧——但顺序不能反。官方 QQ SDK 反过来做
（先记 `lastSeq` 再派发、且不 await handler），进程中途崩溃就会丢事件，
`sessionPersistence` 保证不了至少一次。自己写接收端时务必按
`qqbot.py` / `feishubot.py` 的顺序：`tmp → fsync → rename`，然后才确认。

飞书这条路径上还有一个容易搞错的点：**客户端没有游标**，ack 本身就是提交
点。平台对未 ack 的推送会重试（15 秒、5 分钟、1 小时、6 小时，最多 4 次），
所以语义是至少一次，去重键必须用平台指定的那个——飞书明确要求按
`message_id`（不是 `event_id`）。

推模型的 `poll` 还要检查接收端心跳（`serve-heartbeat`，超过 120 秒视为
故障），否则接收端死掉会表现成「一直没消息」——静默失败，最糟的一种。

## 4. 新增一个通道的最小步骤

1. 写 `examples/<channel>/<channel>bot.py`，实现上面三个动词 + `health`。
   推模型还要多一个 `serve` 动词（收事件 → 先落盘 → 再确认 → touch 心跳），
   并在 README 里写明它必须常驻——它不是驱动，但它是唯一的数据源。
2. 复制 `examples/qq-bot/qq-watch.sh`，只改：
   - 数据目录 / 状态目录的环境变量名（`QQ_*` → `<CHANNEL>_*`）
   - `CLIENT` 指向新客户端
   - `wake` 的 topic 名（`new_qq_messages` → `new_<channel>_messages`）
   - 平台特有的能力判断（例如 QQ 群聊不支持 typing；飞书根本没有 typing，
     就把那条分支整个去掉，而不是留一个永远失败的分支）
   **其余部分不要动**——那部分是六条不变量的实现。
3. 复制 `examples/qq-bot/qq-warm-wait.sh`，改前缀。注意被动回复窗口短的
   平台（QQ 群聊 5 分钟）要把默认空闲时间调小。
4. 测试：`tests/test_qqbot.py` 改造成 `test_<channel>bot.py`，
   `tests/test_qq_hook_integration.py` 改造成对应通道版（`FAKE_*` 环境变量
   驱动 fake 客户端）。集成测试至少覆盖：先排队后提交、空批次也提交、
   提交失败保留队列、损坏队列隔离、单实例锁、崩溃输出算故障。
   协议要手写时（飞书的 protobuf 帧和 WebSocket），再补一个
   `test_<channel>_ws.py`：用**独立的**编解码实现加一个本地回环服务端，
   否则「客户端自己跟自己一致」会让错误实现通过。
5. 在 `examples/<channel>/README.md` 里**先写清楚平台做不到什么**
   （QQ 没有主动推送、窗口只有 5/60 分钟、生产要 IP 白名单；飞书没有
   typing、群聊只投递 @ 消息、推送必须 3 秒内 ack、主动消息受应用可用
   范围限制），再写怎么用。做不到的事要靠文档暴露，不能靠实现假装做到了。
   有英文版的（`README.en.md`）同步写，两份内容不能漂。

## 5. 已经实现的通道

| 通道 | 入口 | 模型 | 已知限制 |
| --- | --- | --- | --- |
| 微信（iLink） | `examples/muse-hook/` | 长轮询 | 登录有效期不定，需重扫 |
| QQ 官方机器人 | `examples/qq-bot/` | 网关推送 | 无主动推送、被动窗口 5/60 分钟、条数上限 4（单聊）/5（群聊）、生产需 IP 白名单 |
| 飞书自建应用 | `examples/feishu-bot/` | 长连接推送 | 无 typing、群聊默认只收 @ 消息、推送须 3 秒内 ack、按 `message_id` 去重、5 QPS、主动消息受应用可用范围限制、只能发文本 |

后续通道（Telegram/Discord/Slack 等）按第 4 节照做即可；每加一个，
驱动层的可靠性逻辑都不需要重写。
